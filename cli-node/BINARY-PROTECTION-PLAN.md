# cli-node 二进制加密保护计划

日期：2026-10-23
状态：设计计划；未实现加密、未发布、未部署。

## 1. 结论与待核实项

- 按用户要求，将 ISPK 列为指定的保护工具候选。
- 当前仓库和已检索资料未能确定 ISPK 的具体工具、厂商、仓库或版本。ISPK 不能直接视为某种已确认安全的密码算法，也不能预设它支持 Linux ELF、Bun、内存加载或授权管理。
- 实施前需要获得 ISPK 的工具来源、版本、Linux x64 支持说明、许可和可自动化构建方式。缺少这些信息不妨碍本计划，但阻止具体工具接入和安全性背书。
- 推荐：成熟保护工具 + 标准认证加密 + 独立发布签名。若 ISPK 是拟定的自有容器名称，再评估受控的薄加载器；不自行设计密码算法，不把自制加载器作为默认捷径。
- 本轮只保护 cli-node，暂不扩展到 kernel、cc-node、OAuth 工具、配置或用户数据。

## 2. 威胁模型与安全边界

目标：提高直接提取嵌入 JS、普通静态逆向、复制分发和修改发布包的成本。

不承诺：

- 运行机 root 无法提取代码或解密材料。
- 防止所有调试、内存导出或修改加载器绕过校验。
- 加密壳等同于许可证系统、不可破解或源码永不泄漏。

保持当前离线启动能力，不默认添加联网激活、硬件指纹绑定、遥测、反虚拟机或反调试。
若目标转为“即使客户控制运行机也不能得到核心实现”，应评估将这部分实现保留在服务端；这属于另一个有联网和运维代价的产品决策。

## 3. 已确认的工程事实

- 当前 cli-node 是 Bun 单文件 Linux x64 ELF，不是普通的全部业务逻辑均为机器码的 C/C++ 程序。
- `scripts/compile-cli-node.ts` 使用 `bun-linux-x64-baseline`，设置 `sourcemap: 'none'`；没有显式启用 `minify` 或 `bytecode`。
- Bun 官方明确说明 bytecode compilation 不隐藏源码，不能把 `--bytecode` 当作代码保密措施。
- 当前已验证源码：独立本地仓库提交 `30b1f60`；生产兼容工作树 `feat/outbound-303@84e6c16`。
- plain ELF：111220864 字节，SHA256 `91402b18768a6c1ce4f78d9dbd779cd5e519906f952f1781213a8649ee31a84a`。
- UPX 基线：27175592 字节，SHA256 `4fb46a0c28bae1675923c0d88ba6a98495e4b1a427a4e1bd260cb80ed2e18e90`；已通过 UPX 自检和压缩后真实链路 e2e 6/6。
- 集群运行环境有 ReadonlyRootfs；不能假设能向容器根目录或 `/tmp` 写入解密后的程序。
- 现有线上校验会比较安装文件和 `/proc/<cli_pid>/exe` 的 SHA256。引入内存加载后，两者可能分别是保护壳和解密后的执行映像，不能继续强求同一个哈希。

## 4. 方案比较

| 方案 | 提供什么 | 局限与选择 |
| --- | --- | --- |
| 现有 UPX | 压缩交付体积，已有功能基线 | 不是加密或可靠防逆向，保留作对照和回滚 |
| 现成 ISPK 保护工具 | 取决于具体产品，当前能力未知 | 先核验来源和 Bun/Linux 兼容性，再决定是否采用 |
| 标准认证加密 + 签名封装 | 磁盘载荷加密、篡改检测、发布来源校验 | 密钥可用时程序才能执行；纯离线分发无法对本机控制者保密 |
| 核心逻辑留在服务端 | 不将这部分实现交付到客户端 | 比单纯加壳更适合强保密，但增加联网依赖，不纳入当前实施范围 |

## 5. 推荐的密码与密钥规则

- 若工具允许选择算法且没有互操作约束，优先考虑成熟库的 XChaCha20-Poly1305：认证加密、较大的 nonce 空间、便于跨 CPU 使用。
- 如果 ISPK 固定采用标准 AES-256-GCM，也可以评估；必须确认 nonce 唯一性、密钥生成与轮换、认证失败处理和 CPU 支持，不能仅看“AES-256”标签。
- 不用 XOR、固定 IV 或自制流密码包装程序。
- 发布来源使用独立公钥签名，例如 Ed25519；签名覆盖载荷、架构、格式版本、构建标识、长度和摘要等受保护元数据。
- 发布签名私钥只在受控构建环境保存，不进入源码、二进制、日志或公开附件；终端只持可信验证公钥。
- 签名解决来源和完整性，不提供内容保密，也不能阻止拥有本机控制权的人修改验证程序。
- 对称解密密钥不能误用 OAuth 凭证或 API key。若为保持离线启动而把解密能力随程序分发，须明确它属于提高提取成本，而不是无法恢复的秘密。

## 6. 构建与加载设计

### 构建

1. 从独立本地 Git 的固定已提交源码构建，拒绝带入其他 WIP。
2. 保留 plain 和当前 UPX 两份基线。先验证 ISPK 处理 plain 的路径，再单独验证 ISPK + UPX 组合，不默认叠加多个壳。
3. 若保护工具自带压缩，使用其支持的流程；压缩应发生在加密之前，不对密文期待有效压缩。
4. 生成保护成品与签名清单；分别登记最终交付文件和内部执行载荷的长度、摘要、工具版本及源提交。
5. 同一源码的加密构建可能因随机 nonce 而不同。记录完整构建输入，不以固定 nonce 换取密文逐字节可重复。

### 加载

- 必须在验签和认证校验成功后，才允许执行对应载荷；错误密钥、损坏或截断必须清楚失败，不能静默运行旧版或未保护版本。
- 优先验证工具的非普通文件落盘加载路径。Linux memfd 可以作为试验选项，但 Bun 内嵌模块和资源能否正常读取必须实跑，不能只依据普通 ELF 的结论。
- 内存加载不等于防 root 导出，也不承诺 plaintext 不会进入 swap 或 core dump。
- 若现有 seccomp、容器或内核策略禁止所需操作，判定方案不兼容；不自动放宽安全策略、不自动改成把明文 ELF 写入普通临时目录。
- 加载器不得额外 daemonize 或改变子进程、PID、信号和退出码语义；不得向 stdout 输出授权横幅、进度或调试文字，以免污染 native JSONL 通信。
- 参数、环境、stdin/stdout/stderr、凭证路径、动态 kernel.json、超时和取消保持原合同。不新增外部访问或读取无关用户文件。

## 7. 实施顺序与停止条件

### A. 工具核验

取得 ISPK 来源与版本，确认 Linux x64/Bun 支持、第三方依赖许可、自动化接口和密钥管理。
无法确定实际工具时停止工具接入，不伪造 ISPK 命令或已支持能力。

### B. 隔离兼容性试验

只使用本地 fixture 和假凭证，试验保护后的程序启动、模块加载、资源访问、协议握手、取消与退出。
先确认普通用户和只读容器均可运行，再考虑优化体积和性能。

### C. 完整验收

- 重新执行已存在的 CCH 历史、303/296 正文兼容性及请求头真实链路 e2e，保护后成品必须全部通过。
- 检查 UA、Accept、UTF-8 Content-Length、gzip JSON / Brotli SSE、CCH 开关和历史内容不变。
- 检查多轮 session、并发、取消后恢复、进程退出、CLI 子进程重启和版本热读取；不能只用 `--version` 判定可用。
- 检查损坏载荷、错误签名、错误密钥、截断和错误架构：不得执行载荷，不得泄漏密钥。
- 检查普通文件和崩溃清理行为；记录启动耗时、峰值 RSS、持续运行和请求延迟。超过现有启动门限或破坏并发/取消行为，不得上线。

### D. 部署与回滚

- 部署清单校验外层保护成品；运行时诊断核对实际执行载荷，两种摘要由可信签名清单关联，不能把内层哈希当作安装文件哈希。
- 更新 `deploy/payload.json` 的最终交付大小和 SHA256，同时明确运行时映像核验规则。不得假报两个文件哈希一致来绕过现有校验。
- 已有镜像、持久 slot-bin、安装模板和运行中映像分别核验；不以模板文件已更新代替实际进程验证。
- 保留已验证的 UPX 版本作为明确的运维回滚项，不作为运行失败后的隐式回退。
- 仅在明确授权部署后，按排空、单槽先行、进程哈希/健康验证再逐槽推进的顺序上线；不重建容器，不改凭证、身份或长期调度状态。

## 8. 本计划的决策

采用标准密码学与独立签名是建议；ISPK 是否为合适的具体实现仍待工具核验。
若 ISPK 只是想采用的容器名称，可以据此设计薄封装；若已有现成产品，优先审查并复用其成熟能力，避免重复实现密码和加载机制。

本阶段不修改 CLI 行为、不加密现有交付文件、不引入授权服务器、不发布或部署。具体实施前唯一必须补齐的信息是 ISPK 的工具来源和版本。
